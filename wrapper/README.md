# Humble

The `Humble` tool (Hard Upper/lower Markov Bounds Library and Executable) is a probabilistic model checker for reachability properties on Markov chains and Markov
decision processes. It reads a model in the [UMB](#model-input) format and computes

```
Pmin=? [ !avoid U target ]      (default)
Pmax=? [ !avoid U target ]      (with -m)
```

The answer is reported as an **interval** — a lower and an upper bound that are guaranteed to
enclose the true probability. The numerics are not done here: `Humble` is a loader and driver
around interval-iteration solvers generated by **Isabelle-LLVM**, whose implementations are
formally verified. This repository contains the C++ frontend that parses the model, builds the
state space, and calls into that generated code.

## Requirements

**An AVX-512F capable CPU.** The solvers perform their interval arithmetic with fused
multiply-adds under an embedded rounding mode (`vfmadd213sd {rd-sae}`), an instruction encoding
that exists only under AVX-512. This is not a tuning choice — it is what makes the computed bounds
sound — and there is no fallback path. On a machine without AVX-512, `Humble` reports this and
exits rather than crashing; run it under an emulator such as
[Intel SDE](https://www.intel.com/content/www/us/en/developer/articles/tool/software-development-emulator.html):

```bash
sde64 -skx -- ./build/humble ...
```

Note that recent Intel desktop/mobile parts (Alder Lake onwards) have AVX-512 disabled, so SDE is
often needed even on new hardware.

Build-time packages:

```bash
apt install cmake clang binutils libarchive-dev nlohmann-json3-dev libboost-all-dev
```

`clang` (plus `ld` and `objcopy` from binutils) is required because the solvers are compiled from
LLVM IR as part of the build. Of Boost, only `program_options` and the header-only `rational` are
used.

The solvers are built from the Isabelle-LLVM output in `generated/` at the repository root:

| file | purpose |
| --- | --- |
| `modest_pmin_gs.ll`, `modest_pmin_gs.h` | Pmin solver (`compute_II`) |
| `modest_pmax_gs.ll`, `modest_pmax_gs.h` | Pmax solver (`compute_pmax`) |

`src/lib_isabelle_llvm.c` is the small allocator shim the generated code calls.

## Building

From the repository root:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
```

To regenerate `generated/` from the theories in `thys/` first, add `-DHUMBLE_BUILD_THEORIES=ON`.
That runs `isabelle build` on the `Maxred_LLVM` session (on Windows through Isabelle's bundled
Cygwin bash), so Isabelle and the AFP sessions it imports must be set up. `isabelle` is looked up on
`PATH` and under `ISABELLE_HOME`, or pass `-DISABELLE_EXECUTABLE=...`; extra arguments go in
`-DISABELLE_BUILD_OPTIONS="..."`.

This compiles the two `.ll` files, gives each solver a private copy of the shared runtime, and
links everything into a single self-contained `build/humble` — there are no shared libraries to
install or to put on a library path. The IR is built at `-O3`; override with
`-DISABELLE_OPT_FLAGS=...` if you need otherwise.

## Usage

```
humble <model.umb> -t <target> [-a <avoid>] [-m] [options]
```

| option | meaning |
| --- | --- |
| `<model.umb>` | the model archive (positional; also `--file`) |
| `-t`, `--target` | atomic proposition marking the target states |
| `-a`, `--avoid` | atomic proposition marking states to avoid |
| `-m`, `--maximize` | compute Pmax instead of Pmin |
| `-x`, `--examine-umb` | list the archive's contents and exit, without analysing |
| `-v`, `--verbose` | report progress, model size, and which files are read |
| `-c`, `--cow` | treat warnings as fatal |
| `--max-iters` | iteration cap (default 100000) |
| `--eps` | convergence threshold (default 1e-6) |
| `--fp-tolerance` | slack in the probability sanity check (default 1e-12) |
| `-h`, `--help` | option summary |

`-t` and `-a` name **atomic propositions carried by the model**, not state formulas; they must be
present in the archive as `annotations/aps/<name>/for-states/values.bin`. Use `-x` to see which
ones a model provides. Omitting `-a` means nothing is avoided. Omitting `-t` leaves the property
trivially unsatisfiable, so `Humble` skips the analysis and exits successfully without printing a
probability.

```console
$ humble examples/dice.umb -t six
Analysis finished for property: Pmin=? [ true U six ]
Reachability Probability: 0.166667 - 0.166667
Solver time: 0.022444 s
Total time: 0.295823 s
```

Every analysis reports two wall-clock timings. **Solver time** is the interval iteration alone —
the generated Isabelle-LLVM code and nothing else. **Total time** covers the whole run, including
command-line handling, decompressing the archive, and building the state space. The gap between
them is the frontend's overhead, which dominates on small models.

(The figures above were recorded under Intel SDE, so they are inflated by emulation; on hardware
with AVX-512 both are substantially lower.)

### Reading the result

The two probabilities are a lower and an upper bound. Their width reflects how far interval iteration was
run: tighten it with a smaller `--eps` (at the cost of more iterations), and raise `--max-iters` if
the bounds are wider than expected.

How faithful the bounds are depends on how the model stores its branch probabilities:

- **`rational`** — converted to floating point with outward rounding, so the interval is a sound
  enclosure of the exact probabilities.
- **`double`** — used as given, and `Humble` warns. The result can only be trusted to the extent
  that the probabilities in the file are themselves exact; a value that was already rounded when
  the model was generated cannot be recovered here. Use `-c` to make that warning fatal if you
  need the stronger guarantee.

## Model input

A `.umb` file is a tar archive holding an `index.json` description plus flat binary arrays for the
transition structure, branch probabilities, and state annotations. `Humble` reads the transition
system, the initial state, and the two atomic propositions named on the command line; rewards,
actions, and state valuations are ignored.

The format is still evolving and stamps its version in `index.json`. Both **v0** (PRISM 4.9 and
earlier) and **v1** (PRISM 4.10) are read, and the layout is chosen from that stamp rather than
guessed. A newer revision of a known version is read with a warning; an unknown major version is
refused rather than misparsed.

Discrete-time chains and MDPs are accepted, as are continuous-time chains — for unbounded
reachability the exit rates do not matter, so the embedded chain gives the same answer. A model
with no state index is treated as having one choice per state.

On loading, every choice is checked against

    1 - tolerance <= sum(lb) <= 1     and     1 <= sum(ub) <= 1 + tolerance

Breaching one of the bounds at 1 means no probability distribution fits inside the intervals, so
the model is wrong. `Humble` reports this and carries on regardless — a malformed distribution may
well be deliberate, and correcting it is not the tool's business. Pass `-c` to make these warnings
fatal instead. The sums are accumulated with directed rounding, so a warning reflects the model
rather than the checker's own arithmetic.

**Interval MDPs are not supported.** A model whose branch probabilities are interval-valued
(`double-interval`) is rejected. The solver treats a branch interval as a rounding enclosure of one
exact probability rather than as model uncertainty, and would otherwise report bounds outside
[0, 1].

## Limitations

- The `queries.json` part of the UMB format is not read, so properties come from the command line
  rather than from the model. Whether to minimise or maximise is chosen with `-m`.
- Only unbounded reachability (`P=? [ !a U b ]`) is supported — no step bounds, rewards, or nested
  properties.
- The reported probability is for the model's first initial state; a warning is issued if there is
  more than one.
- Memory is held for the process lifetime: the state space points directly into the decompressed
  archive buffers, which are never freed.
- There is no automated test suite. `examples/` holds models to check by hand.

## Repository layout

```
headers/   frontend headers, including the neutral solver interface
src/       UMB and state-space loaders, CLI, solver translation units
examples/  sample .umb models (not in version control)
```

`src/pmin_solver.cpp` and `src/pmax_solver.cpp` are deliberately separate translation units: the
two generated headers define the same C types behind different include guards and cannot both be
included in one file.
